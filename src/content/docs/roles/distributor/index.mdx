After an SBOM has been created, it needs to reach the people or tools that will use it. This is the **distribute** step.
A recipient of an SBOM may be internal (e.g. a security team) or external (e.g. a customer or regulator), which can result in quite different approaches of how to share the SBOM.

## Approaches to share an SBOM

Which method is the right one depends on the purpose.
Some examples include:

- **Deliver it with the software:** Include it in a package, container image, installer, or release download.
- **Along the Source Code:** Publish it next to the source code or release files.
- **Through an API:** Send it directly to another system, such as a vulnerability management tool.
- **Through a customer portal:** Make it available only to customers or other approved users.
- **On request:** Send it by email or another agreed channel when someone asks for it.

For open-source software, publishing the SBOM with the source code or release is often the easiest option. For commercial or internal software, a portal, repository, or API may be more suitable.

## What to check before sharing

The SBOM should be connected to the software it describes. Before sharing it, check:

- Does it describe the correct product and version?
- Is it in a format the recipient can use, such as SPDX or CycloneDX?
- Is it clear where and how the recipient can get it?
- Is the file still up to date?
- If it was changed or combined with another SBOM, is that clear?
- Are the information in the SBOM are approved for sharing?

Keep the original SBOM when converting it to another format or adding information. This makes it easier to understand where the information came from and to fix problems later.

<Aside type="tip" title="SBOM Extensions">
Please note that SBOMs can be extended with addition information, such as VEX to communicate vulnerability status, CSAF to communicate security advisories, or attestation to ensure the integrity of the SBOM.
If you are sharing an SBOM, consider whether you should also share these related documents.
An overview of the SBOM extensions can be found in the [SBOM Extensions](../sbom_basics/sbom_extensions)
</Aside>

# Transparency Exchange API

The [Transparency Exchange API (TEA)](https://github.com/CycloneDX/transparency-exchange-api) is a common way for software producers and consumers to exchange SBOMs automatically.

With TEA, a producer can provide a known online service. A consumer's tool can then ask that service which SBOMs are available and retrieve the one for the product and version it needs.

In simple terms:

1. The producer or distributor makes an exchange service available.
2. The consumer's tool connects to that service.
3. The tool looks for the product, release, or other software identifier.
4. The service returns the matching SBOM or related information.
5. The tool downloads the document and can process it automatically.

This is useful when many products, suppliers, or releases need to be handled.
It reduces manual downloads and makes it easier to find updates.
TEA is also designed to support other types of BOMs and supply-chain information, not only software SBOMs.

For more information, please checkout the [Repository of the Project](https://github.com/CycloneDX/transparency-exchange-api).
