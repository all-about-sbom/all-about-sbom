At the beginning an SBOM needs to be generated.
Even though people often refer to “the SBOM,” there is actually no such thing.
An SBOM can be generated at various stages of software development.
There is no right or wrong time to do this, but you have to keep in mind that different things are described at different generation times:

<Steps>
1. **Based on Source Code:**
    This section describes which components are specified in the source code. Some types, such as dynamic linking, cannot be reliably detected here because they are not loaded until runtime.

2. **During the Build Process:**
    This allows you to identify all components that are actually integrated by the compiler/build process.

3. **On a running System:**
    Some components are loaded only at runtime and can therefore be identified with certainty only on the system where the program is running. This applies, for example, to dynamic linking. However, it is important to note that in this case, an SBOM no longer describes a universal system, but rather a specific system.
</Steps>

## SBOM Basics
An SBOM is a formal record of the software components that make up a software product.
It usually is a json or xml file that lists all components, their versions, and their relationships.
To learn more about the basics of SBOMs and find examples, check out the [SBOM Basics](../../sbom_basics).

## Types of SBOMs
To account for the differences arising from the various generation timepoints, the [BSI](https://www.bsi.bund.de/SharedDocs/Downloads/EN/BSI/Publications/TechGuidelines/TR03183/BSI-TR-03183-2_v2_1_0.pdf), in collaboration with [CISA](https://www.cisa.gov/resources-tools/resources/types-software-bill-materials-sbom), has defined six formal types of SBOMs:

| SBOM Type | Definition | Data Description |
| --- | --- | --- |
| **Design** | SBOM of an intended, planned software project or product with included components, some of which may not yet exist, for a new software artifact. | Typically derived from a design specification, request for proposal (RFP), or initial concept. |
| **Source** | SBOM created directly from the development environment, source files, and included dependencies used to build a product artifact. | Typically generated from software composition analysis (SCA) tooling, with manual clarifications. |
| **Build** | SBOM generated as part of the process of building the software to create a releasable artifact, such as an executable or package, from source files, dependencies, built components, build-process data, and other SBOMs. | Typically generated as part of a build process. It may combine intermediate Build and Source SBOMs for a final release artifact SBOM. |
| **Analyzed** | SBOM generated by analyzing artifacts such as executables, packages, containers, and virtual machine images after the build. This analysis generally requires a variety of heuristics. In some contexts, this is also called a “3rd party” SBOM. | Typically generated by third-party tooling that analyzes software artifacts. |
| **Deployed** | SBOM that provides an inventory of software present on a system. It may combine other SBOMs with configuration information and an examination of execution behavior in a deployment environment. | Typically generated by recording the SBOMs and configuration information of artifacts installed on systems. |
| **Runtime** | SBOM generated by observing a running system, including components that are loaded dynamically during execution. | Typically generated by instrumenting or monitoring a running system. |

Source: [CISA](https://www.cisa.gov/resources-tools/resources/types-software-bill-materials-sbom)


## Choosing an SBOM Tool
There are many open-source and commercial tools available for generating SBOMs. We provide detailed information on our [tooling site](../../tooling).

Some popular open-source SBOM generation tools include:

- [Syft](https://github.com/anchore/syft)
- [Trivy](https://github.com/aquasecurity/trivy)
- [Cdxgen](https://github.com/cdxgen/cdxgen)
