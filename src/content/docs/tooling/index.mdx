The market for SBOM tools has grown significantly in recent years, making it increasingly difficult to find the right tool for one's specific needs.
This page helps you structure the decision-making process and provides links to existing catalogs where you can get an overview of the available solutions.

However, before moving on to tool selection, it is important to reach an agreement with all stakeholders on what the requirements for the tool are.

---

## What Kind of Tools Exist?

SBOM tools are most usefully organized by the function they perform rather than the format they support.
The functional taxonomy established by the NTIA and carried forward in [CISA guidance](https://www.ntia.gov/sites/default/files/publications/ntia_sbom_tooling_taxonomy-2021mar30_0.pdf) defines three primary categories.
It describes the role a tool plays in an SBOM workflow, not necessarily a separate product or product category.
Many tools combine several types, and a single platform may support all three categories.

| Category | Tool types | Overall approach |
| --- | --- | --- |
| **Produce** | Build, Analyze, Edit | Tools for creating SBOMs by integrating into the build process, analyzing source code or binary artifacts, or supporting manual creation and editing of SBOM data. |
| **Consume** | View, Diff, Import | Tools that make SBOMs interpretable for humans, e.g. by visualizing the information, comparing multiple SBOMs, or enabling the discovery, retrieval, and import of an SBOM into your system. |
| **Transform** | Translate, Merge, Tool support | Tools that transform an SBOM, e.g. by converting it to a different format, merging multiple SBOMs into one, or providing APIs and libraries to enable other tools to use the SBOM data. |

<details>
<summary><strong>Produce — SBOM generation and authoring</strong></summary>

Produce tools create or author SBOMs. The NTIA taxonomy identifies three approaches:

**What these tools do:**
- **Build:** Automatically create an SBOM as part of building a software artifact, including information about the build
- **Analyze:** Inspect source or binary files and associated sources to generate an SBOM
- **Edit:** Assist a person with manually entering or editing SBOM data

**What varies between tools in this category:**
- Which SBOM types they support — source, build, binary-analyzed, runtime, and design SBOMs each require different approaches
- Which ecosystems, languages, and package managers they recognize
- Whether they integrate into CI/CD pipelines, developer IDEs, or operate as standalone utilities
- The accuracy of component identification, particularly for transitive dependencies and components not delivered via package managers

<Aside type="note">
A tool that generates valid SPDX or CycloneDX does not necessarily produce a complete or accurate SBOM.
The [2026 CISA Minimum Elements](https://www.cisa.gov/resources-tools/resources/2026-minimum-elements-software-bill-materials-sbom) notes that SBOM quality and completeness vary significantly based on the tools and methods used to generate the SBOM, and recommends including generation tool metadata in the SBOM itself so consumers can assess reliability.
This finding is in line with academic evaluations of SBOM generation tools, which have found that many tools fail to identify all components and transitive dependencies in a software artifact.
If you are interested in understanding how well different types of components are detected, the paper [Poking Around in the Dark: Why a Shared Understanding of Components Matters](https://arxiv.org/abs/2606.02442) can be a starting point.
</Aside>

</details>

<details>
<summary><strong>Consume — SBOM ingestion, viewing, and analysis</strong></summary>

Consume tools use existing SBOMs and make their data available for review, comparison, retrieval, and downstream operations. The NTIA taxonomy identifies three approaches:

**What these tools do:**
- **View:** Present SBOM contents in a human-readable form to support decision-making and business processes
- **Diff:** Compare multiple SBOMs and clearly show their differences, such as changes between software versions
- **Import:** Discover, retrieve, and import an SBOM into a system for further processing and analysis

**What varies between tools in this category:**
- Which import formats and SBOM format versions are supported
- The depth and currency of vulnerability correlation, including KEV and EPSS scoring integration
- VEX/CSAF ingestion support and how findings are filtered and surfaced
- Whether the tool supports linking of received SBOMs to asset records

This category is especially relevant to organizations receiving SBOMs from vendors — see [Receiving and Using SBOMs](/roles/consumer) for the operational context.

</details>

<details>
<summary><strong>Transform — SBOM conversion, aggregation, and export</strong></summary>

Transform tools operate on existing SBOM data to adapt or connect it for another purpose. The NTIA taxonomy identifies three approaches:

**What these tools do:**
- **Translate:** Change an SBOM from one file type to another while preserving the same information. This includes converting between SPDX and CycloneDX formats, as well as between different versions of the same format
- **Merge:** Combine multiple SBOMs or other data sources for analysis and audit purposes
- **Tool support:** Enable use in other tools through APIs, object models, libraries, transport, or other reference sources

**What varies between tools in this category:**
- Which format conversions are supported and whether conversion is lossless
- Whether aggregation preserves provenance and signing from source SBOMs
- Integration depth with external systems (ingestion only vs. bidirectional)

<Aside type="caution">
Format interoperability between tools is not guaranteed. Interoperability between different tools handling SBOMs is not currently guaranteed, due to varying interpretations of the SBOM specifications. When selecting tools across categories, verify that the output of a Produce or Transform tool can be correctly ingested by the Consume tools in the same workflow.
</Aside>

</details>

## Evaluating Tools for Your Organization

The NTIA taxonomy describes what a tool does.
Selecting a tool requires criteria for deciding whether it fits an organization's needs, environment, and operations.
The questions below help the **Chooser** — the person or team responsible for selecting tooling — to identify criteria for selecting the right tool.

No single tool is right for every organization.
Select only the categories and attributes that apply to your use case, then use the same criteria for every candidate:

- **Function and coverage:** Which Produce, Consume, or Transform types are required? Which formats, SBOM types, ecosystems, and versions must the tool support?
- **Deployment and data handling:** Where may the tool run, and where may source code, binaries, SBOMs, or vulnerability data be stored and processed?
- **Integration and operation:** How will it connect to CI/CD, asset management, vulnerability management, ticketing, or other systems? Consider APIs, command-line interfaces, webhooks, plugins, and import/export behavior.
- **Access and security:** Does it support the organization's requirements for authentication, authorization, audit logs, encryption, secrets management, and tenant isolation?
- **Cost, licensing, and support:** What are the license terms and total operating costs, including infrastructure, usage limits, support, training, and additional modules? Who maintains the tool and delivers security updates?
- **Product context:** Is SBOM functionality the tool's primary purpose or one feature of a broader platform? Which requirements need additional validation because SBOM functionality is not the product's main focus?

### Practical evaluation process

1. **Agree on requirements.** Mark each criterion as required, preferred, or not needed, and identify approval gates.
2. **Shortlist candidates.** Use the catalogs below and vendor documentation to find tools that meet the required functions and formats. Exclude candidates that fail an approval gate.
3. **Compare and validate.** Ask the same questions of each candidate. Verify unresolved requirements with representative SBOMs, workflows, or a focused proof of concept.
4. **Approve the choice.** Document the selected tool, accepted gaps, owner, and implementation plan, then complete the organization's approval process.
